Multi-tenancy

Varias empresas (tenants) comparten la misma instalación; cada una ve solo sus datos.

El patrón

Las tablas operativas llevan una columna tenant_id. Toda consulta filtra por el tenant de la sesión con este patrón:

WHERE (%s IS NULL OR tenant_id = %s)

El valor sale de get_tenant_filter() (modules/context.py), que lee tenant_id de la sesión de Flask, y se pasa dos veces como parámetro.

tenant_id en sesiónQuiénResultado
Un IDUsuario de un tenantSolo las filas de ese tenant.
NULLSuperadminTodas las filas.

No omitir el filtro. Una consulta operativa sin este patrón expone datos de otros tenants. Aplica a lecturas, actualizaciones y borrados.

Claves únicas

Los códigos de negocio son únicos dentro de cada tenant, no en toda la base: se definen como índice compuesto con nombre uk_<tabla>_<columna>_tenant en modules/schema_generator.py.

Qué no depende del tenant

  • La asignación de rutas a roles vale para todos los tenants. Ver Roles y permisos.
  • La conexión a la base operativa es una sola por instalación.

En integraciones

  • Intercambio: cada registro lleva tenant_codigo, que se resuelve contra tenants.codigo.
  • API REST: cada token pertenece a un tenant y todos los endpoints quedan acotados a él.
  • En las URLs de tenants y usuarios del panel admin, el ID de tenant va codificado (encode_id / decode_id), no como entero.
