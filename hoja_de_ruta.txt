2.1 CSRF Protection
--------------------
Instalar: pip install Flask-WTF

Archivo: app.py
  from flask_wtf.csrf import CSRFProtect
  csrf = CSRFProtect(app)

  En cada <form> HTML agregar:
    <input type="hidden" name="csrf_token" value="{{ csrf_token() }}">

  En cada AJAX POST agregar header:
    'X-CSRFToken': document.querySelector('meta[name=csrf-token]').content

  En base.html agregar:
    <meta name="csrf-token" content="{{ csrf_token() }}">

  Excepcion: rutas AJAX que devuelven JSON (batch imports) necesitan
  el token en header, no en body.

========================================================================
NOTA TECNICA: PROBLEMA DE ENCODING EN WINDOWS (resuelto)
========================================================================

 Problema: El cliente MySQL/MariaDB en Windows lee archivos SQL usando
 la codificacion del sistema (CP1252 para Windows en español), NO UTF-8.
 Esto causa que caracteres acentuados como 'ó' (0xC3 0xB3 en UTF-8)
 se interpreten como dos caracteres separados ('Ã³'), rompiendo el SQL.

 Solucion implementada en schema_completo.sql:
   1. Archivo 100% ASCII-safe (sin caracteres acentuados en comentarios)
   2. La columna 'descipción' de tipoubicacion se crea como 'descipcion'
      y se renombra via prepared statement al final del script:
      
      SET @new_col = CONCAT('descipci', UNHEX('C3B3'));
      SET @sql = CONCAT('ALTER TABLE tipoubicacion CHANGE COLUMN ...');
      PREPARE stmt FROM @sql;
      EXECUTE stmt;
   
   3. UNHEX('C3B3') inyecta directamente los bytes UTF-8 correctos
      (0xC3 0xB3) para el caracter 'ó', evitando conversiones de charset.

 Lesson learned: En entornos Windows/XAMPP, siempre usar archivos SQL
 100% ASCII y generar caracteres especiales via UNHEX() o CHAR() en
 prepared statements cuando sea necesario.
